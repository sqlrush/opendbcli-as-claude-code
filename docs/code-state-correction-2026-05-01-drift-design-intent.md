# 修正：drift 机制的设计意图

日期：2026-05-01
触发场景：用户问"drift 机制 + 0.05 阈值是为了让小模型不至于上下文污染吗"

## 当时错误的认知

上一轮回答里我说：
> "小模型上下文敏感 — opendb 要兼容 9B/27B 自部署小模型，context 短 + 容易被旧 tool result 带偏"

把 drift 机制的设计动机归因到"小模型适配"。

## 实际状态（grep CHANGELOG 后）

`docs/CHANGELOG.md:745-751` v1.1.10 (2026-04-25) 原文：

> [P2] 主题漂移检测
> - 基于 Jaccard 相似度比对新 user message 和上一条 user message 的词元集合
> - 中文按字切分 + 英文按词切分 + 常见停用词过滤
> - engine.go 在 session load 之后调用：如果检测到主题漂移就丢弃历史，让 LLM 从干净上下文起步
> - 阈值 0.05 保守取值，避免误伤"继续分析"这类同主题关键词少的续问

实际设计意图：
- ✅ 防 session 上下文污染（通用机制，不分模型大小）
- ✅ 0.05 是**保守取值**，目的是**少误伤同主题续问**（与"激进清理"相反）
- ❌ 没有任何关于"小模型"的考虑

## 关键证据

- `docs/CHANGELOG.md:745-751` 完整原文，无"小模型"字眼
- `internal/engine/context/drift.go:13` 注释也只说阈值的语义（0.0/0.1/0.3 三档），没提模型规模
- `git log -- internal/engine/context/drift.go` 显示该文件单一提交 `11ebd571 v1.1.10`，无后续 tweak

## 设计意图 vs 实际表现的 gap

原设计的内部逻辑：0.05 = 保守 = 尽量保留历史

实际效果与设计预期不符：
- 中文按字切分 + 短问场景下，"当前数据库存在什么问题" vs "到底哪些表 VACUUM"
  Jaccard = 0/23 = 0
- 用户感觉同话题，算法判 drift
- 0.05 阈值没起到"保守保留"作用 —— Jaccard 本身在中文短问下太脆弱

这是**算法选择**与**意图**脱节，不是阈值数字调错。改阈值（0.15、0.30）只会拉高跨话题误判率，治不了本。

## 反思教训

1. CLAUDE.md "架构与功能问答规范" 明确要求基于扫描结果回答，不要"凭印象/推测"
2. 我之前编"为小模型"的理由，逻辑上"看似合理"，但**没有任何代码或文档证据支持**
3. 看到用户问"是不是 X" 时，第一反应不应该是"对呀差不多"，而应该是 grep CHANGELOG / 注释 / commit 信息确认 X 是否真的是 X
