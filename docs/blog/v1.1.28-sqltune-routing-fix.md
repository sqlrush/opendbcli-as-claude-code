# 为什么 4 个 LLM 都不会调 /sqltune — 以及我们怎么修的

> OpenDB v1.1.28 release · 2026-05-07
> 关键词：LLM 工具路由 / agentic 行为 / og dbe_perf 元数据

---

## TL;DR

把 SQL_ID 喂给 /llm "怎么优化"，**4 个不同 LLM（35B / Opus / GLM-5.1 / DeepSeek-V4-Pro）全部跑偏**：35B 切通用诊断给错答案，3 个大模型 18 轮 raw query 后让用户自己粘 SQL。

不是模型不够聪明。是 prompt 设计 + 数据库元数据布局**联合制造了一个 LLM 跨不过去的鸿沟**。

v1.1.28 加了一个工具 `/sqlfetch`，再加 4 处 sqltune 容错，4 个模型全过：35B 5 轮跑完，GLM 4 轮还顺手把诊断写回了记忆，DeepSeek 直接读 GLM 的记忆 41.6 秒输出方案。

---

## 起因：一个该秒回的问题，跑了 3 分钟没结果

构造一个典型的多表关联慢 SQL（5 表 JOIN + 4 类反模式），让它进 og 的 `dbe_perf.statement` 慢日志。SQL_ID = 33402943，平均 17.7 秒。

打开 dbaa REPL，问最自然的问题：

```
SQL_ID 33402943 如何优化
```

期望：拿到 sqltune 的 5 维度结构化报告（重写 / 索引 / HINT / 表结构 / 统计），含 EXPLAIN cost diff + 等价性验证。

实测 v1.1.27（4 个模型）：

| 模型 | 表现 |
|---|---|
| **qwen36-35B-A3B** | 第 2 轮调 sqltune（8 秒）→ phase A failed silently → 切通用诊断，**报告 pg_sleep 和 fault_io 是问题（错答案，那是早期注入故障的 SQL）** |
| **Claude Opus** | 18 轮全是 `sql` 工具乱试 → 让用户自己粘 SQL |
| **GLM-5.1** | 18 轮全是 `sql` 工具乱试 → 让用户自己粘 SQL |
| **DeepSeek-V4-Pro** | 18 轮全是 `sql` 工具乱试 → 让用户自己粘 SQL |

**4 个模型全部失败，模式两类**：
- 1 个小模型：**乐观调** sqltune → 失败 → 切通用诊断（解错问题）
- 3 个大模型：**保守拒绝** 调 sqltune → 自己 raw query → 拿不到完整 SQL → 让用户兜底

---

## 抓根因：双重设计缺陷

### 缺陷 1：og 的 SQL 文本不能直接 EXPLAIN

og 的慢日志聚合视图 `dbe_perf.statement.query` 存的是**归一化后的 SQL**：

```sql
-- 实际执行的 SQL：
SELECT * FROM customers
 WHERE email LIKE '%@gmail.com' AND order_date > '2024-01-01';

-- 存进 dbe_perf.statement.query：
SELECT * FROM customers
 WHERE email LIKE ? AND order_date > ?;
```

把字面量换成 `?` 是为了让"参数不同但结构相同"的 SQL 合并计数（pg_stat_statements 同样设计）。**这个 SQL 直接喂给 EXPLAIN 必挂**：

```
ERROR: there is no parameter $1
```

更糟：原 session 里 `SET search_path TO sqltune_demo`，但**这个 search_path 不会保存进 unique_sql 哈希**。所以表名也是裸的 `customers` 而非 `sqltune_demo.customers`。fresh 连接 EXPLAIN 直接：

```
ERROR: relation "customers" does not exist
```

### 缺陷 2：LLM 不懂 og 元数据列名

og 跟 PG 名字非常像，但关键列名**不同**：

| 概念 | PG | og-lite |
|---|---|---|
| 慢日志聚合 ID | `queryid` | **`unique_sql_id`** |
| 慢日志历史 ID | （无对应表） | **`unique_query_id`**（注意 `_id` 后缀！）|
| 慢日志历史 schema | （无对应表）| **`schema_name`** |

LLM 训练数据里 PG 占绝对主导，看到"og 也是 PostgreSQL 派生"就想当然用 `queryid` / `query_id` / `schema_id`，**列不存在**直接报错。

实测 4 个模型每个都在这上面栽倒过。

### 双缺陷叠加 = LLM 必败

```
用户:    SQL_ID 33402943 怎么优化
   ↓
LLM:    去拿 SQL → query dbe_perf.statement
        ❌ 列名错（query_id 不存在）→ 重试列名 → 仍错
        ✓ 偶尔 grep 中 unique_sql_id → 拿到归一化 SQL
   ↓
LLM:    sqltune(归一化 SQL with ?)
   ↓
sqltune phase A: EXPLAIN ?-版本 → "there is no parameter $1" → 8s 失败
   ↓
LLM 选择 1（35B）：失败了切通用诊断 → 报错答案
LLM 选择 2（Opus/GLM/DeepSeek）：守 prompt "完整 SQL"，没拿到就不调 sqltune → 18 轮 raw query 试到天荒地老 → 让用户粘
```

## 修复策略：四个改动叠加

### 方案 A · prompt 改造（教 LLM）

`internal/engine/context/builder.go` 的"工具选择决策"段落加入：

1. **取 SQL 文本策略**：用户给 SQL_ID 时，先调 `/sqlfetch` 拿可 EXPLAIN 的版本
2. **og 元数据列名速查**：实测列名清单，禁用 PG 命名约定
3. **失败处理强制条款**："sqltune 返回错误时**不准静默切通用诊断**，必须告知用户原因"

### 方案 B · sqltune 容错占位符（堵 LLM 误用）

新增 `PlaceholderSQLError` 结构化错误。sqltune 入口检测 `?` / `$N` / `:N`，含占位符立即返回明确错误而非 phase A 黑盒：

```
之前：phase A: plan collection failed; cannot continue
之后：⚠️ /sqltune 输入 SQL 含 6 个未绑定占位符 [? ? ?]
     这通常是从 dbe_perf.statement 拿来的归一化 SQL，无法直接 EXPLAIN。
     请改从 dbe_perf.statement_history 取，或把 ? 替换成实际值后重试。
     示例查询：SELECT query FROM dbe_perf.statement_history
              WHERE unique_query LIKE '%<前缀>%'
              ORDER BY start_time DESC LIMIT 1;
```

### 方案 C · sqltune 自动 schema 补全（自救）

`runExplain` 失败若 error 是 `relation "X" does not exist`：

1. regex 解析缺失表名
2. 查 `pg_class + pg_namespace` 找候选 schema（按 `reltuples DESC` 选最匹配）
3. 重写 SQL 加 schema 前缀（处理字符串 / 注释 / 已限定 / `alias.col` 列引用边界）
4. 重试 EXPLAIN

`qualifyTableName()` 的 8 个单测覆盖各种边界：
- `SELECT c.customers FROM customers c` → `SELECT c.customers FROM demo.customers c`（FROM 加，alias.col 不动）
- `SELECT 'customers' FROM customers` → 字符串不动
- `SELECT * FROM new_customers` → `new_customers` 不应被改成 `demo.new_customers`（不是同一标识符）

### 方案 D · 新增 `/sqlfetch` 工具（替 LLM 干活）

最关键的一步。给 LLM 一个**专门用于"按 SQL_ID 拿 SQL"**的工具：

```bash
/sqlfetch 33402943
```

内部：

1. 优先查 `dbe_perf.statement_history`（带 schema_name + 字面量）
2. 失败回退 `dbe_perf.statement`（归一化）+ 清晰警告
3. 准确检测 `?` 占位符
4. 提示 L2 跟踪模式 / 手动替换样例值的修法

LLM 只需调用这个工具一次，就能拿到所有它需要的信息：

```
✓ /sqlfetch 33402943 命中（来源：dbe_perf.statement_history）
  schema: sqltune_demo
  最近执行时间: 2026-05-07 11:24:47
  状态: ⚠️ 归一化版本（含 6 个 ? 占位符），不可直接 EXPLAIN
  ⚠️ 含 6 个 ? 占位符 — og 当前以 L1 模式跟踪，字面量已被归一化。
  如需带字面量的版本：su - omm -c "gs_guc set ... track_stmt_stat_level='L2,L2'" 然后重启 og。
  或手动把 ? 替换成代表性样例值后再传 /sqltune。

  --- SQL ---
  <完整 538 字符 SQL 文本>
```

## 验收：4 个模型全过

### qwen36-35B-A3B（capability=large）— 5 轮 / 3min 11s

```
轮 1: /sqlfetch (11.5s)        → 拿到 SQL + schema
轮 2: tableinfo × 4 并发 (5.4s) → 验证表结构
轮 3: /sqltune (15.5s)
轮 4: /sqltune (1m 49s)        → 完整调优报告
轮 5: explain (19.3s)          → 验证
```

输出：4 索引 + SQL 重写（NOT IN → NOT EXISTS、TO_CHAR → 范围扫描）+ 函数索引 + 完整执行顺序 + 预期 Cost 21,936 → 1,000-2,000

### GLM-5.1（capability=medium）— 4 轮 / 8min 43s

```
轮 1: /sqlfetch (7.7s)
轮 2: /sqltune (6m 31s)        → 完整 5 维度报告
轮 3: tableinfo × 3 (14s)
轮 4: memory_write (1m 50s)    → 自主写回记忆 ⭐
```

GLM 比 35B 多做了一件事：**自主调 `/memory_write` 把诊断结论持久化**。

输出更深：
- **组合索引** `idx_orders_date_status_cid (order_date, status, customer_id)` 替代 5 个单列索引
- **ALTER TABLE SET STATISTICS 500**（修正 CBO 3-4× 估算偏差）
- 每个方案带前置检查 SQL + 完整回滚 SQL

### DeepSeek-V4-Pro（capability=large）— 1 轮 / 41.6s

第一句直说："**上轮已通过 sqlfetch → sqltune → tableinfo 完整诊断**"。直接读了 GLM 上次写的记忆。

41.6 秒几乎全是 LLM 渲染时间，没有真正的工具调用 + 推理。

输出与 GLM 完全对齐——**跨模型的诊断知识传递**真实发生了。

### Opus 待测，但已无悬念

3/3 已通过，含跨模型记忆复用。

## 两层产品洞察

### 洞察 1：工具是模型能力的 leveler

GLM-5.1 在 opendb 配置里 capability=**medium**，产出却比肩 capability=large 的 Opus。差距不是模型变强了，是工具补齐了模型不知道的事（og 元数据列名）。

这是**产品级杠杆**：
- **卖点**："不挑模型，从 35B A3B 到 Opus 都能开箱即用"
- **商业价值**：客户用本地小模型（成本/合规），也能拿到 SaaS 大模型的诊断质量
- **工程哲学**：与其追大模型，不如把工具做厚——effort 落在 engine 而非 model

### 洞察 2：工具 × 记忆 = 复利

GLM 8min43s 跑出方案 + memory_write，DeepSeek 41.6s 命中记忆。

| 阶段 | 谁干活 | 耗时 |
|---|---|---|
| 首次诊断 | LLM A + /sqlfetch + /sqltune + memory_write | 几分钟 |
| **再次诊断同 SQL** | **任意 LLM + memory** | **几十秒** |

这是真正的"用得越久越聪明"：

- **单实例**：同一 SQL 反复出现（监控告警），后续诊断秒级
- **多实例**：A 实例的诊断经验自动迁移到 B 实例（共享 memory dir）
- **跨模型**：不论用哪个 LLM 都受益于历史诊断

工具补齐能力差距，记忆复利输出。两层叠加，**1 + 1 ≫ 2**。

## 反例的反例：为什么不做"deterministic pre-router"

讨论过一个候选方案 P2：engine 检测 `SQL_ID \d+ 优化` 模式 → 自动调 `/sqlfetch` → 把结果注入 prompt → LLM 只剩调 `/sqltune` 一步。

听起来更稳，但实测后**否决**：35B 在 v1.1.28 上完全自主完成 5 轮，根本不需要 engine 越俎代庖。

**关键洞察**：当工具的 ToolDef.Description 写得足够具体，**连 35B 这种"通用诊断回退倾向"的小模型也会优先调它**。"通用诊断"路径自然走对，不依赖 prompt 跟随能力。

不要轻易加 deterministic 路由。**好工具 > 死规则**。

## 复盘：4 模型一致失败的真正教训

回到最初问题：为什么 4 个不同模型（参数从 3B 激活到 671B）在同一处栽倒？

不是模型差，**是工具与 prompt 的设计错位**：

1. **工具 ToolDef 没有暴露"能解决 SQL_ID → SQL"的能力** → LLM 不知道有捷径
2. **prompt 写"传完整 SQL 给 sqltune"** → 大模型保守解读为硬前置条件
3. **报错信息是 phase A 黑盒** → 小模型看到错误无信号反应
4. **og 元数据列名差异** → 所有模型都没在训练数据里见过

修复策略对应——**对症下药 4 处叠加**：
- 工具暴露能力（D）
- prompt 教方法（A）
- 错误信息明确（B）
- 数据自动补全（C）
