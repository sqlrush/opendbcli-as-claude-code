### 核心判断

Qwen3.6 35B-A3B 在 PromptToolAdapter 模式下展现出**强结构化输出 + 强跨轮上下文** 但**弱工具循环收敛**的典型特征。优势集中在:报告类任务(S2 WDR)严格引用工具返回数据零编造;跨轮上下文召回稳定(F 4.6/5,在所有维度中最高),R2/R3 都能准确回引 R1 的具体数字。

短板有三:**(1) 工具循环不收敛** —— S1 R2 跑 19 轮、R3 跑 18 轮,反复调用 vacuum/autovacuum/bloat 同一组工具仍未拿到表名,缺乏"换思路"的能力。**(2) SQL 参数自修复弱** —— S1 中 `pg_stat_user_tables` 字段引用错误一直没修正,最终只能用 `<表名>` 占位符交差。**(3) 可执行方案降级** —— S3 R3 在 EXPLAIN 不可用时直接给"通常慢 10-30%"的凭空数字,而不是构造样例数据;S4 R3 在无 session 时不给通用 kill 模板。

### v1.2.x 改进建议

1. **轮数硬限 + 工具去重检测**:S1 R2/R3 连续 18-19 轮中,vacuum/autovacuum 各被调 5+ 次,bloat 被调 6+ 次。建议在 parser 层加"同工具相同/相似 args 在最近 5 轮内重复 ≥3 次"触发软警告,提示模型转换策略或交付当前结论。
2. **SQL 工具错误反馈强化**:S1 R2 自述"在 pg_stat_user_tables 视图上存在字段引用问题",但不自我修正。建议把 SQL 错误响应中的字段名建议(`HINT: Perhaps you meant ...`)显式回传给 LLM,而非吞掉。
3. **占位符兜底**:S1 R3 输出 `VACUUM ANALYZE <表名>; -- 替换为实际表名`。建议在 prompt 里加"若最终方案仍含 `<占位>`,必须先调用 sql 查询补齐,否则视为未完成"。
4. **跨场景一致性校验**:S3 R1 判定 SQL_ID 4175761868 对应的表不存在,但 S2 WDR 报告里同 SQL_ID 是已成功执行 1.3s 的 `CREATE INDEX IF NOT EXISTS`。建议在 sqltune 失败时,引导模型把 SQL 文本和 WDR 中该 SQL 的执行历史(call_count, elapsed)交叉对照,而不是直接断"表不存在"。
5. **追问追到底**:S4 R1 已经发现"longtx 1 个",但 R2 用户问"哪个用户跑的什么 SQL" 时,只调了 locks/blocktree/sql 1 轮就放弃了 longtx 那条线索。建议在 prompt 中明确"用户追问的对象若与上一轮某工具的非零结果相关,必须重新调用该工具拿详情"。
