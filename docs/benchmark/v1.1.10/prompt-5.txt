## 紧急措施

数据库侧无需改动。请按以下顺序自查应用侧：

```sql
-- 1. 在数据库 psql 命令行直接打时间，验证内核耗时
\timing on
SELECT * FROM bench_t5 WHERE uid=123;
\timing off
```

```sql
-- 2. 用 EXPLAIN ANALYZE 确认实际执行时间（非估算）
EXPLAIN (ANALYZE, BUFFERS, TIMING) SELECT * FROM bench_t5 WHERE uid=123;
```

如果上面两条都是亚毫秒级（预期会是），那么"慢"来自以下任一处，与 DB 无关：

1. **网络 RTT**：客户端到 OG 实例的链路延迟（跨区/跨机房）
2. **应用层 ORM**：是否在循环里反复执行（N+1 问题）
3. **连接建立开销**：每次新建连接而非复用（建议用连接池/PgBouncer）
4. **未使用绑定变量**：每次 uid 值都不同会触发硬解析（虽然有 [Bypass] 仍建议用预编译语句）
5. **客户端渲染**：终端/IDE 输出 100 万行数据时实际是因为缺 LIMIT，而不是 uid=123 这条
6. **session 级别 GUC**：例如 `set enable_bitmapscan=off` 等手动关闭过优化器特性

## 根因修复

### 方案 1: 改用绑定变量（防止后续值变化时硬解析）
- **操作**：
```sql
PREPARE q1(int) AS SELECT * FROM bench_t5 WHERE uid=$1;
EXECUTE q1(123);
```
- **⚠️ 风险评估**：无，只是会话级 prepare
- **📋 前置检查**：无
- **🔄 回滚方案**：`DEALLOCATE q1;`

### 方案 2: 如果应用层是 N+1 调用，改批量查询
- **操作**：
```sql
SELECT * FROM bench_t5 WHERE uid = ANY(ARRAY[123, 124, 125, ...]);
```
- **⚠️ 风险评估**：单条 SQL 一次拉多行，IN 列表过大时（>1000）改临时表 JOIN
- **📋 前置检查**：确认应用层确实存在 N+1 模式
- **🔄 回滚方案**：保留原单条调用即可

### 方案 3: 不需要在 DB 侧做任何改动
- 当前 explain 显示的 [Bypass] + Index Scan + cost 8.27 已经是该查询能达到的最优形态
- 不要 CREATE 新索引、不要 VACUUM FULL、不要改优化器参数 — 都不会让它更快
