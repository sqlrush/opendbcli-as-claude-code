- 这些 `pg_sleep(15…)` 会话每个都开启了显式事务（`BEGIN`），属于 idle in transaction 风险源。如果持续累积，会持有 snapshot 阻止 VACUUM 回收死元组、推高 xid_age。当前 /waits 未观察到对应等待事件，但属于值得关注的隐患。来源：/activesessions
- /longtx 工具已被调用并返回 20 个长事务记录条目，与 /activesessions 中观察到的 `pg_sleep(15…)` 会话规模一致，进一步印证这批会话以长事务形式驻留。来源：/longtx
- WLM 采集会话已运行 31 分钟，属于后台常驻线程，不是异常。来源：/activesessions
- PROFILE.md 为空白模板，本实例无历史基线可参照。来源：/profile

### 紧急措施（可立即执行）
如果确认这批 `pg_sleep` 会话是测试残留、可以清理：

```sql
-- 1) 先 review 即将被终止的会话
SELECT pid, usename, datname, state, xact_start, query
FROM pg_stat_activity
WHERE query LIKE '%pg_sleep(15%';

-- 2) 确认无误后再终止
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE query LIKE '%pg_sleep(15%';
```

- ⚠️ 风险评估：会强制断开这些会话；如果是真实业务在用 pg_sleep（罕见），会导致业务报错
- 📋 前置检查：先用上面第 1 条 SELECT 确认全部都是 `gauss/postgres` 上的测试连接
- 🔄 回滚方案：会话被终止后无法回滚，但客户端可重连重跑
