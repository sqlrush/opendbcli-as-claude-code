## 紧急措施

```sql
-- 实测瞬时 WAL 增速
SELECT now(), pg_current_wal_lsn(),
       pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0') AS total_bytes;
-- 间隔 60s 再跑一次，差值 = 每分钟 WAL 字节数
```

```sql
-- 看 checkpoint 实际写入量（补全本轮缺失的 /checkpoint 数据）

```

```sql
-- 按写块数（而非返回行数）找写入热点 SQL
SELECT unique_sql_id, n_calls,
       n_tuples_inserted, n_tuples_updated, n_tuples_deleted,
       LEFT(query, 120) AS query
  FROM dbe_perf.statement
 ORDER BY (COALESCE(n_tuples_inserted,0)
         + COALESCE(n_tuples_updated,0)
         + COALESCE(n_tuples_deleted,0)) DESC
 LIMIT 10;
```

## 根因修复

**本轮证据不支撑"WAL 异常"结论，无需做修复操作**。

如后续实测证实 WAL 增速 > 数百 MB/min，再按以下方向定位：

### 方向 1: 如确认 checkpoint 偏频繁放大 FPW

- **操作**:
  ```sql
  ALTER SYSTEM SET checkpoint_timeout = '30min';
  ALTER SYSTEM SET max_wal_size = '4GB';
  SELECT pg_reload_conf();
  ```
- **⚠️ 风险评估**: checkpoint 间隔拉长会延长崩溃恢复时间；max_wal_size 增大会占更多 pg_wal 磁盘
- **📋 前置检查**: 确认 pg_wal 分区剩余空间；确认业务能容忍更长 crash recovery
- **🔄 回滚方案**: `ALTER SYSTEM RESET checkpoint_timeout; ALTER SYSTEM RESET max_wal_size; SELECT pg_reload_conf();`

### 方向 2: 如发现高频写 SQL 是源头

- 待补充查询的 `n_tuples_inserted/updated/deleted` 排序结果出来后，针对具体 SQL 做批量提交、合并写入或 COPY 替代逐条 INSERT
