# v1.1.09 vs v1.1.10 Benchmark 对比报告

**测试时间**: 2026-04-25
**主体模型**: GLM-5（智谱 744B MoE）
**评估口径**: 总耗时、轮次、输出结构、可执行性、四层覆盖、显著回归
**载荷**: 同一套 OG 5.0 实例（47.251.30.180:15432），预先 setup 6 类压力（长事务/idle in tx/索引膨胀/checkpoint 频繁/bench_t5/bench_t8）

## 一、量化指标

| 指标 | v1.1.09 | v1.1.10 | Δ |
|------|---------|---------|---|
| 总耗时 | 1047s | **1519s** | **+45%** |
| 平均耗时/prompt | 105s | 152s | +45% |
| 总轮次（去掉 timeout） | 62 | 36 | **-42%** |
| 平均/round 耗时 | 16.9s | **42.2s** | **+150%** |
| Prompt timeout 数 | 1（p6） | 1（p10） | 持平 |
| 输出空文件数 | 1（p6） | 1（p10） | 持平 |

**核心数据反差**：v1.1.10 用了**少一半**的工具调用，但每一轮的 LLM 处理时间是 v1.1.09 的 **2.5 倍**。

### 单 prompt 对照

| Prompt | 场景 | v1.09 时间/轮 | v1.10 时间/轮 | Δ时间 | 评估 |
|--------|------|---------------|---------------|-------|------|
| p1 | 模糊"越来越慢" | 108s / 6r | 138s / 5r | +30s | 持平偏慢 |
| p2 | 单表查询慢 | 67s / 8r | 131s / 5r | +64s | **回归** |
| p3 | 连接数快满了 | 34s / 2r | 176s / 6r | +142s | **严重回归**（但更诚实） |
| p4 | WAL 增长快 | 111s / 4r | 176s / 4r | +65s | 回归 |
| p5 | bench_t5 慢 | 141s / **20r** | 142s / 4r | -1s | **质量大幅提升** |
| p6 | 续问（drift 测试） | **180s timeout** | 156s / 1r | -24s | **核心 bug 修复** |
| p7 | "换个话题" | 43s / 3r | 137s / 4r | +94s | **过度结构化** |
| p8 | VACUUM 后空间涨 | 147s / 12r | 162s / 4r | +15s | 持平 |
| p9 | 系统整体慢 | 139s / 5r | 121s / 3r | -18s | **改进** |
| p10 | 完整健康报告 | 77s / 2r | **180s timeout** | +103s | **严重回归** |

**轮次缩减亮点**: p5（20→4 轮，-80%）、p8（12→4 轮，-67%）—— v1.1.09 的 dedup cache 在 v1.1.10 上把 LLM "工具循环" 行为彻底压住了。

## 二、质量分析

### 显著改进

**P6: MessageCountTrigger 直接救场**

v1.1.09: 180s 超时，0 字节输出
v1.1.10: 156s, 1 轮，3.5K 字节高质量输出

v1.1.10 prompt-6 在续问场景下：
- 触发了 `MessageCountTrigger=15` 主动压缩，把 prompt-5 的 4 轮工具历史折叠成摘要
- 一轮就完成诊断，给出 4 个具体修复方案（PreparedStatement / global plancache / 覆盖索引 / Bypass 路径）
- 每个方案都包含「操作 / 风险 / 前置检查 / 回滚」四要素

**这是 v1.1.10 想解决的核心问题，效果完全达预期。**

**P5: dedup cache 抑制工具循环**

v1.1.09 跑了 20 轮还在反复调 explain/tableinfo。v1.1.10 4 轮就识别出"内核侧无瓶颈，问题在客户端"，并给出 `\timing` 验证步骤。质量明显更高。

**P9: 整体调用链效率提升**

5→3 轮，139→121s，结论一致。

### 显著回归

**P3: dedup cache 反噬**

v1.1.09 (34s, 2r)：直接给出 "12/200, 6%, 没满"（但 12 个连接和 setup 不一致，说明 v1.09 的 sessions 工具拿到的是部分快照）。

v1.1.10 (176s, 6r)：sessions 工具返回了 62 个会话，但 LLM 试图再调 sql/params 拿 max_connections 时被 dedup cache 拦截（"已查过"），最终只能写"不能凭默认值 200 推算 31%"，转而提供给用户的 SQL 让用户自己跑。

**这其实是更诚实的行为**（拒绝编造数据），但用户感知是"问了 3 分钟没给答案"。

**P7: 四层结构过度泛化**

v1.1.09 (43s, 3r)："当前实例未配置逻辑复制，不存在复制延迟问题。" — 一行答完。
v1.1.10 (137s, 4r)：完整的"## 一/二/三/四"四层 + 表格 + 后续 SQL 建议。

`profile/opengauss.go` 加的 few-shot 示例本意是规范复杂诊断的输出。但 LLM 把它泛化到了所有 prompt，对单点查询过度输出。

**根因**: few-shot 示例的"严格模仿这个粒度"提示太强，原本"单点查询不强制四层"的 escape clause 被压住了。

**P10: 服务端 timeout（最严重）**

v1.1.09 (77s, 2r): 完整健康报告，6 个章节（内存/WAL/复制/VACUUM/索引/会话）+ 综合评估。
v1.1.10: 180s 超时，0 字节输出。

prompt 10 要求覆盖 6 个领域，每个领域都要查工具。v1.1.10 的 LLM 在每个领域都试图按 few-shot 示例的粒度输出，加上每轮 LLM 处理时间 +150%，叠加起来超出 180s 上限。

## 三、根因分析

### 慢主因：每轮 LLM 处理时间 +150%

```
v1.1.09: 总耗时 / 总轮次 = 1047 / 62 = 16.9s/round
v1.1.10: 总耗时 / 总轮次 = 1519 / 36 = 42.2s/round  (扣除 timeout 后估算)
```

可能的解释（按概率排序）:

1. **Few-shot 示例膨胀 system prompt** — `profile/opengauss.go` 加的 worked example 约 700-1000 tokens。每轮 LLM 调用都走这个 prompt，叠加输入 token 增加。
2. **Cache miss 概率上升** — system prompt 内容变化导致 prompt cache 命中率降低（v1.1.10 加了 cache_control 但首轮仍是 miss）。
3. **GLM-5 API 当时延迟波动** — 不可控，但单点偏差不应解释跨 9 个 prompt 的一致 +150%。
4. **新增 telemetry/drift/compress 的开销** — 微秒级，可忽略。

最可能是 #1 + #2 叠加。需要测 cache 命中率才能确认（v1.1.10 telemetry 已加，但本次 benchmark 还没跑出有效缓存数据）。

### 轮次减半主因：v1.1.09 dedup + v1.1.10 强制压缩组合拳

- v1.1.09 已经加了 `(name,args)→content` dedup cache
- v1.1.10 加了 MessageCountTrigger 主动压缩
- 两者组合让 LLM 不再陷入"反复探查同一对象"的循环
- 副作用：当 LLM 想在新角度再查同一工具时（如 p3 想验证 max_connections），被拦截后只能放弃或转嫁给用户

| 输出有效字节数 | ~31K | ~36K | 1.16 | ✓ |
| 严重度分级覆盖 | 5/9 | 8/9 | 1.6 | ✓ |
| 修复 SQL 可执行率 | ~80% | ~95% | 1.19 | ✓ |
| 总耗时 | 1047s | 1519s | 0.69 | ✗ |

**强制验收 4/5 通过；耗时维度未通过。**

### 期望验收（≥ v1.1.09 × 1.05）

显著超过的：四层结构覆盖率（v1.09 有 5/9 prompt 用了，v1.10 有 9/9）、修复方案完整度（含风险/回滚）、续问场景质量（p6 从 timeout 救回到 1 轮 high-quality）。

显著低于的：响应速度（-31%）、对简单问题的简洁性。

**期望验收：质量维度全部超过 1.05，速度维度 0.69 — 不达标。**

## 五、定性结论

v1.1.10 是一次 **质量↑速度↓ 的 trade-off**：

✅ **真做对的**:
- p6 续问 timeout 修复（核心目标）
- p5 工具循环抑制（20→4 轮）
- 输出结构化、可执行性、严重度分级 全面提升

❌ **没做对的**:
- p10 健康报告 timeout（few-shot 副作用，对长任务尤其致命）
- p7 简单问题被四层结构过度包装（few-shot 副作用）
- 总耗时 +45%（per-round latency 翻倍）

⚠️ **中性的**:
- p3 慢但更诚实（拒绝编造，让用户自己跑 SQL）

## 六、立即建议（v1.1.11 候选）

按价值/工作量排序：

1. **【P0】Few-shot 示例瘦身** — 把 `opengauss.go` 加的 worked example 从 ~30 行缩到 ~10 行，保留结构示意但去掉细节文字。预计 per-round 耗时可降 30%。

2. **【P0】单点查询 escape clause 加强** — 在 few-shot 示例后明确加："只有满足"模糊问题/全面诊断"两类 prompt 才用四层；'查 X 是多少' / '换个话题查 Y' 等明确单点查询直接给答案 + 来源。"

3. **【P1】并行工具调用** — orchestrator 让独立工具（/memory + /xid + /params + /sessions）并发执行。健康报告类 prompt（p10）能直接砍 50% 时间，同时不影响 LLM 逻辑。

4. **【P1】MaxDiagnosisTimeout 提到 240s** — 当前 180s 对全面健康报告太紧，p10 已多次撞这个墙。提到 240s 给四层完整输出留余量。

5. **【P2】Cache hit telemetry 真实验证** — v1.1.10 的 telemetry 已就位，下版可基于 cache log 直接看出 system prompt 是不是 cache miss 的主因。
