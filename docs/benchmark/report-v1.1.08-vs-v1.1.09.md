### 3.2 Prompt 2 — Index Bloat（v1.1.09 从超时救回）

**Prompt**：`有张表的查询越来越慢`

#### v1.1.08 输出（180s 超时 / 0B）

空输出。日志显示 14 轮后仍未收敛，反复调用 /topsql /bloat /vacuum /tableinfo 等工具但没形成结论就超时。

#### v1.1.09 输出（67s / 8 轮 / 675B）

```
根据目前查询结果：
- **慢SQL日志**：没有超过 1000ms 的慢查询记录
- **Top SQL**：都是监控类查询，没有明显业务查询
- **表膨胀**：检测到 **2 个表存在死元组膨胀**（dead > 5%）

## 需要补充信息
"越来越慢"可能是多种原因，请告诉我：
1. **表名是什么？**（schema.table）
2. **什么查询慢？**
```

8 轮内识别问题（bloat 表 2 个），并明确提示 prompt 本身信息不足，要求用户补充。

**说明**：
- v1.1.08 的 13/14 轮死循环是经典的"重复调用"症状（无去重机制）。
- v1.1.09 的 dedup cache 有效防止了重复调用。
- 同时 v1.1.09 诚实承认需要用户补充信息，而不是盲目 guessing（符合数据验证规则）。

**评分**: v1.1.08 **0.0** → v1.1.09 **6.5**（**+6.5**，因 v1.1.08 零输出）

### 3.3 Prompt 6 — 续问（v1.1.09 严重回归）⚠️

**Prompt**：`针对刚才的发现给修复 SQL 和长期建议`（紧接 prompt 5 的 session 复用）

#### v1.1.08 输出（68s / 6 轮 / 833B）

```
**诊断失败，无法给出修复方案**

上一轮工具调用出现异常，explain 和 sql 工具均未返回有效数据。
根据规范要求，诊断结论必须基于实际工具返回的数据，我不能编造表结构...

**请重新描述问题，我将从头开始诊断：**
1. 确认 bench_t5 表在哪个 schema
2. 获取表结构和索引信息
3. 执行 EXPLAIN 分析查询计划
4. 给出精准的修复方案
```

虽然未成功诊断，但**明确拒绝编造**（数据验证规则生效）+ 给出明确的后续步骤。

#### v1.1.09 输出（180s 超时 / 0B）

完全空输出，超时未返回。

#### 回归根因分析（Opus 判断）

v1.1.09 引入了两个放大 prompt 6 难度的改动：
1. **Session 复用**加载了 prompt 5 的 history（prompt 5 跑了 20 轮，message 积累多）
2. **四层策略 + profile 密度扩充**使单次请求的 input token 比 v1.1.08 多 ~30%

Session 复用 + prompt 膨胀叠加下，prompt 6 的 GLM-5 请求在处理超长 context 时陷入反复调用工具的循环直到 180s 超时。

**这是本版本唯一的严重倒退点**。

**评分**: v1.1.08 5.5 → v1.1.09 **0.0**（**-5.5**）

## 6. 发版建议

### 6.1 是否发 v1.1.09？

**可发，但需要配合 follow-up**。

- 强制验收达标（+8.5% > -2%）
- 期望验收达标（+8.5% > +5%）
- 代码本身稳定（57 个 internal 包测试全绿）
- 除 Prompt 6 外所有场景要么持平要么明显提升

### 6.2 v1.1.09 回归风险清单

| 风险 | 描述 | mitigation |
|---|---|---|
| Prompt 6 续问超时 | v1.1.08 68s → v1.1.09 180s(timeout) | 用户可用 `/session new` 绕过（已加入 v1.1.09）；长远需监控 session 累积 msg 的压缩触发 |
| Session 累积 + 大 prompt 叠加 | 长对话时 token 线性增长 | 下版本做 MaybeCompress 触发阈值调整 + 基于主题相似度的早期压缩 |
| GLM-5 API 偶发 503 | 本次测试遇到过 API 过载 | 非本项目问题；provider 层 retry(5 次) 已 cover 大多数情况 |

### 6.3 推荐的 v1.1.10 跟进项（基于 benchmark 发现）

按 ROI 排序：
1. **续问场景 context 管理** — 针对 prompt 6 回归，加基于"session message 数 > N"的主动压缩（P0）
2. **Prompt Cache telemetry** — 暴露 cache_hit/cache_miss 指标到 `opendb --version` 或 `/sessions stats`（P1）
3. **主题漂移检测** — 两轮 /llm 间检测关键词重叠，低于阈值建议 `/session new`（P2）
4. **四层策略 few-shot 示例** — profile 里加 1-2 个具体示例，让小模型更稳定遵守（P2）

---

## 7. 结论

### v1.1.09 is a net positive (+8.5%)

v1.1.09 的 6 个 P0/P1 优化在 benchmark 中验证有效：
- 工具速查表 + dedup 防护使长时间/多轮场景显著变快（prompt 2 从超时 180s → 67s）
- 四层诊断策略让多工具场景输出更结构化（prompt 1/10 严重度分级）
- 加权总分 +8.5%，超过期望验收门槛

### 单一回归点需 follow-up

Prompt 6 续问超时是 v1.1.08 session 复用机制 + v1.1.09 prompt 膨胀叠加导致的，**不是 v1.1.09 独立引入的 bug**，但 v1.1.09 使之更易触发。`/session new` 提供了用户侧 workaround；v1.1.10 应从 context 压缩角度根治。

### 决策

**建议发 v1.1.09，在 CHANGELOG 明确标注 prompt 6 场景的限制 + 推荐用户遇到续问慢时执行 `/session new`**。
