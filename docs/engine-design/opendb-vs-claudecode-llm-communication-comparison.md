# OpenDB vs Claude Code：LLM 通信对比分析报告

> 日期：2026-04-03
> 目标：识别 OpenDB 与 Claude Code 在 LLM 通信效率、准确性方面的差距，指导优化方向

---

## 一、架构总览对比

```
┌─────────────────────────────────────────────────────────────────────┐
│                         Claude Code                                  │
│                                                                      │
│  用户输入 → 20步处理管线 → Opus                                       │
│  ┌──────────────────────────────────────────────┐                    │
│  │ A.输入预处理(6步) → B.上下文注入(2步,30+种)    │                    │
│  │ → C.压缩裁剪(4层) → D.上下文组装(3步)          │                    │
│  │ → E.消息规范化(11子步) → F.API准备(3步)        │                    │
│  └──────────────────────────────────────────────┘                    │
│  while(true) { callModel → if tool_use → execute → continue }       │
│  错误恢复: 413→compress, 529→retry/fallback, max_tokens→upgrade      │
│  10层重试 + 模型降级 + 流式工具执行 + prompt cache                    │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│                           OpenDB                                     │
│                                                                      │
│  用户输入 → ClassifyInput → dispatchNaturalLanguage                   │
│  ┌──────────────────────────────────────────────┐                    │
│  │ 构建 systemPrompt + 压缩report                │                    │
│  │ → AgentLoop(native) 或 PromptLoop(text)       │                    │
│  └──────────────────────────────────────────────┘                    │
│  for turn := 0; turn < maxTurns; turn++ {                            │
│    provider.Chat → if toolCalls → executeTool → continue             │
│  }                                                                   │
│  无重试 / 无压缩 / 无cache / 无模型降级                                │
└─────────────────────────────────────────────────────────────────────┘
```

## 二、20 维度逐项对比

### 1. Prompt 构造策略

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **策略** | Context Engineering — 不改写用户输入，环绕注入丰富上下文 | 简单拼接 — systemPrompt + compressedReport + userInput | 🔴 重大差距 |
| **系统提示** | ~30KB，几十个章节，含行为规范/工具使用/风格/安全/环境信息 | ~500字，仅描述角色 + 工具列表 + 诊断规则 | 🔴 重大差距 |
| **上下文层数** | 8层：系统提示 / Git状态 / CLAUDE.md / @附件 / 30+自动附件 / 嵌套记忆 / Hooks / system-reminder | 2层：系统提示 / 压缩报告 | 🔴 重大差距 |

**分析：** Claude Code 的核心设计哲学是"不改写用户的话，但给模型提供完整的决策依据"。OpenDB 目前只给了模型最基本的角色描述和工具列表，缺乏行为规范、环境上下文、项目规则等关键信息。

### 2. 系统提示工程

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **行为规范** | 15+ 条任务执行规则（先读再改、先诊断再换策略、不加多余功能等） | 11 条诊断规则（禁编造、每轮1-2个skill、必须给结论等） | 🟡 部分差距 |
| **工具使用指南** | 详细指导用哪个工具替代什么（Read代替cat、Edit代替sed等） | 仅列出可用skill名称，无使用策略指导 | 🔴 重大差距 |
| **输出风格** | 精确控制：不用emoji、简短直接、引用格式（file:line）、markdown | 格式模板（根因分析/紧急措施/根因修复），但缺乏精细风格控制 | 🟡 部分差距 |
| **安全约束** | 5层权限控制 + 危险操作具体示例 + 确认机制 | 工具分安全级别 + readOnlyFilter | 🟢 基本够用 |
| **环境信息** | CWD、平台、Shell、OS版本、模型名、知识截止、是否git仓库 | 无 | 🔴 缺失 |

### 3. 上下文注入

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **项目规则** | CLAUDE.md 四级加载（Managed→User→Project→Local） | 无等价机制 | 🔴 缺失 |
| **Git 状态** | 分支、main分支、近5次提交、status（memoized，截断2KB） | 无 | 🟡 N/A（数据库项目） |
| **文件引用** | @file#L10-20 解析，独立附件消息 | 无等价机制 | 🟡 场景不同 |
| **自动附件** | 30+ 种：IDE状态、诊断信息、任务提醒、日期变化、MCP指令等 | 1种：compressedReport（Sentinel异常报告） | 🔴 重大差距 |
| **嵌套记忆** | 操作子目录时自动加载该目录的 .claude/rules/*.md | 无 | 🟡 场景不同 |
| **Hooks** | 用户可配置提交前钩子，注入额外上下文 | 无 | 🟡 未来可考虑 |
| **隐藏消息** | `<system-reminder>` + `isMeta:true` — 模型看到但用户看不到 | 无等价机制 | 🔴 缺失 |

### 4. Agent Loop（核心循环）

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **循环结构** | `while(true)` 异步生成器，无固定轮数限制 | `for turn < maxTurns`，硬限制（默认10-20轮） | 🟡 设计选择不同 |
| **停止条件** | `len(tool_use) == 0` → 完成 | `len(toolCalls) == 0` → 完成，或达到maxTurns | 🟢 基本一致 |
| **收敛引导** | 无（靠模型自主判断） | maxTurns-2时注入收敛提示："请在本轮直接给出最终诊断" | 🟢 OpenDB更好 |
| **双路径** | 单路径（native function calling） | 双路径：AgentLoop(native) + PromptLoop(text模拟) | 🟢 OpenDB兼容性更好 |

### 5. 工具执行

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **并发模型** | 只读工具并发（max 10），写入工具串行 | 全部串行执行 | 🔴 差距 |
| **流式执行** | StreamingToolExecutor — 模型还在输出时就开始执行工具 | 等模型完整输出后才解析执行 | 🔴 差距 |
| **结果截断** | 50KB+ → 写磁盘 + 内联前2KB + 路径引用，模型可用Read读全文 | MySQL/PG: 3000字符硬截断；Oracle: 无截断 | 🔴 重大差距 |
| **结果预算** | `applyToolResultBudget()` — 按工具定义的 maxResultSizeChars 动态控制 | 无预算机制 | 🔴 缺失 |

### 6. 错误处理与重试

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **HTTP 重试** | 指数退避（500ms base, max 32s, 10次），含 jitter | 无重试 | 🔴 重大差距 |
| **429 限流** | 检查 Retry-After header，<20s 保留fast mode，>20s 降速 | 无处理 | 🔴 缺失 |
| **529 过载** | 3次连续后切 fallback model（Opus→Sonnet） | 无处理 | 🔴 缺失 |
| **413 过大** | contextCollapse drain → reactiveCompact → retry | 无处理 | 🔴 缺失 |
| **max_output_tokens** | 升级 8k→64k + 注入"Resume directly..."（最多3次） | 无处理 | 🔴 缺失 |
| **流式失败** | 丢弃部分结果 + tombstone孤立工具 + 重新创建executor + 非流式重试 | 无流式恢复 | 🔴 缺失 |
| **工具执行失败** | 错误消息写入 tool_result，loop 继续 | 错误消息写入 tool message，loop 继续 | 🟢 一致 |

### 7. 上下文窗口管理

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **压缩层级** | 5层：Snip → Micro → Collapse → Auto → Reactive | 无压缩 | 🔴 重大差距 |
| **Auto Compact** | 超过阈值时 fork 总结agent生成摘要，替换旧消息，模型无感知 | 无 | 🔴 缺失 |
| **Context Collapse** | 多轮工具调用折叠为摘要（比auto compact便宜且可逆） | 无 | 🔴 缺失 |
| **Token 预算检查** | 95% 容量时阻止 API 调用，防止 413 | 无 | 🔴 缺失 |
| **token 追踪** | 精确记录 inputTokens/outputTokens，计算剩余预算 | Usage 结构体有但未用于决策 | 🔴 未利用 |

### 8. Prompt Cache

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **系统提示缓存** | 分块缓存：org级（跨用户共享）+ global级（1P跨组织） | 无 | 🔴 缺失 |
| **消息缓存** | 倒数1-2条消息标记 cache_control，利用 ephemeral/1h TTL | 无 | 🔴 缺失 |
| **cache_edits** | micro compact 通过 cache_edits 删除 KV cache 旧段 | 无 | 🔴 缺失 |
| **成本影响** | cache hit 减少 90% input token 成本 | 每次全量发送 | 🔴 成本浪费 |

### 9. 模型参数调优

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **Thinking** | `thinking: { type: 'adaptive' }` — 模型自主决定是否深度推理 | 无 | 🔴 缺失 |
| **Effort** | `output_config.effort` — 控制推理力度 | 无 | 🔴 缺失 |
| **Speed** | `speed: 'fast'` — 不降低能力前提下加速 | 无 | 🟡 N/A |
| **Task Budget** | `output_config.task_budget` — 告知模型剩余 token 预算 | 无 | 🔴 缺失 |
| **Temperature** | thinking 启用时 =1.0 | 可选配置，默认不设置 | 🟢 灵活 |
| **Max Tokens** | 8K默认，可动态升级至64K | 可配 `max_result_tokens` | 🟡 基本够用 |

### 10. 流式处理

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **响应流式** | 全程 SSE streaming，idle watchdog 防挂起 | ChatStream 接口存在但诊断流程仅最后一轮使用 | 🟡 部分实现 |
| **中间轮流式** | 每轮都流式 | 中间轮同步，仅最后一轮流式 | 🟡 差距 |
| **工具流式执行** | 模型输出过程中就启动工具执行 | 等完整响应后才开始 | 🔴 差距 |
| **思维过滤** | 实时过滤 `<think>` 标签，只展示内容 | PromptLoop 有实时过滤 | 🟢 一致 |

### 11. 模型降级与容错

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **模型降级** | Opus → Sonnet 自动降级（连续529错误） | 无自动降级 | 🔴 缺失 |
| **策略降级** | 无（始终用同一策略） | AutonomousStrategy → GuidedStrategy（设计中，未实现） | 🟢 OpenDB设计更好 |
| **规则兜底** | 无（纯 LLM） | 有规则引擎兜底（无 LLM 时降级） | 🟢 OpenDB更可靠 |

### 12. 工具描述与发现

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **描述生成** | `tool.prompt()` 动态生成，每次API调用时实时计算 | 静态写在 system prompt 中 | 🟡 差距 |
| **Schema** | `zodToJsonSchema` 自动转换 + strict模式 | OpenAI function 格式或文本描述 | 🟡 差距 |
| **延迟加载** | `defer_loading: true`，按需通过 tool search 发现 | 全部预加载 | 🟡 场景不同 |
| **工具发现** | skill_discovery 自动附件列出可用 skills | skill 列表写死在 prompt 中 | 🟡 差距 |

### 13. 消息格式处理

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **规范化** | 11步处理：附件上浮、虚拟消息过滤、连续user合并、thinking清理等 | 无规范化处理 | 🔴 差距 |
| **角色验证** | 严格保证 user/assistant 交替 | 依赖 OpenAI 兼容格式自然保证 | 🟡 基本够用 |
| **大结果处理** | 写磁盘 + 内联摘要 + 路径引用 | 硬截断或无截断 | 🔴 差距 |

### 14. 会话管理

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **会话持久化** | 对话历史持久化到磁盘，支持恢复 | 仅内存中维护当次诊断 | 🟡 场景不同 |
| **无限对话** | autocompact 保证对话不被窗口限制 | 单次诊断10-20轮后结束 | 🟡 场景不同 |
| **跨轮上下文** | 完整对话历史 + 压缩摘要 | 完整对话历史（但无压缩） | 🟡 可能不足 |

### 15. Thinking/Reasoning 处理

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **Adaptive Thinking** | 模型自主决定是否需要深度推理 | 无 | 🔴 缺失 |
| **Thinking 提取** | 仅用于内部（thinking块不发给用户） | 提取 `<think>` 内容，未展示给用户 | 🟡 一致 |
| **Thinking 清理** | compaction后清理不匹配的thinking签名 | 无（不做compaction） | 🟡 N/A |

### 16. 可观测性

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **API 遥测** | 精细遥测：retry次数/延迟/错误/provider/cache命中/stall时长 | 无遥测 | 🔴 缺失 |
| **Token 统计** | 精确追踪 input/output/cache_read/cache_creation tokens | Usage 记录但未展示或利用 | 🔴 未利用 |
| **轮次追踪** | turnCount + transition reason | onRound回调 + 轮次日志 | 🟡 基本够用 |

### 17. 错误隔离

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **附件隔离** | 每个附件用 `maybe()` 包裹，一个失败不影响其他 | 无等价机制 | 🔴 缺失 |
| **工具隔离** | 工具失败后 loop 继续，错误传给模型自行判断 | 工具失败后 loop 继续 | 🟢 一致 |
| **级联防护** | 子abort控制器，兄弟工具错误不影响其他工具 | 无 | 🟡 差距 |

### 18. 安全与权限

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **权限模型** | 5层：allow/deny规则 → pre-tool hooks → tool.checkPermissions → 交互确认 → 审计 | 4层：L0只读 → L1操作 → L2管理 → L3危险 | 🟢 各有特色 |
| **输入验证** | 工具参数 zod schema 严格验证 | skill.Validate() 参数验证 | 🟢 一致 |

### 19. 多模型支持

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **Provider** | 原生 Anthropic API + Bedrock + Vertex | OpenAI兼容 + Ollama | 🟢 各有侧重 |
| **模型切换** | 运行时可切 fast/standard；fallback到Sonnet | `/model switch` 运行时切换 | 🟢 一致 |
| **能力适配** | 固定用 Opus/Sonnet（不按能力分策略） | 按 capability(small/large) 选策略 | 🟢 OpenDB更灵活 |

### 20. 性能优化

| 维度 | Claude Code | OpenDB | 差距评估 |
|------|------------|--------|---------|
| **Prompt Cache** | 3层缓存（session/org/global），减90%成本 | 无 | 🔴 重大差距 |
| **并行工具** | 只读工具10并发 | 全部串行 | 🔴 差距 |
| **流式执行** | 模型输出时预执行 | 等完整输出 | 🔴 差距 |
| **Memoize** | git状态/CLAUDE.md/工具schema会话级缓存 | 无会话级缓存 | 🟡 差距 |
| **增量工具描述** | MCP instructions delta — 只发变化的工具 | 每次全量发 | 🟡 差距 |

## 四、优化优先级建议

### P0：核心通信质量（直接影响诊断准确性）

| # | 优化项 | 预期收益 | 复杂度 |
|---|--------|---------|--------|
| 1 | **重构系统提示** — 从500字扩展到结构化系统提示，含行为规范、工具使用策略、输出格式、环境信息 | 诊断准确性提升30%+ | 中 |
| 2 | **工具使用策略指导** — 不只列出工具名，详细说明每个工具什么场景用、怎么组合用 | 减少无效工具调用 | 低 |
| 3 | **结果截断优化** — 从硬截断3000字改为智能截断（保留关键信息 + 路径引用） | 减少信息丢失 | 中 |
| 4 | **thinking/adaptive** — 支持 Anthropic API 的 adaptive thinking 参数 | 复杂诊断准确性提升 | 低 |

### P1：通信可靠性（直接影响用户体验）

| # | 优化项 | 预期收益 | 复杂度 |
|---|--------|---------|--------|
| 5 | **HTTP 重试 + 指数退避** — 429/5xx 自动重试，含 jitter | 消除间歇性失败 | 低 |
| 6 | **上下文窗口管理** — token计数 + 阈值检查 + 简单压缩（截断旧轮次） | 防止长诊断超窗口 | 中 |
| 7 | **max_output_tokens 恢复** — 检测输出截断，自动升级限制并续写 | 防止诊断被截断 | 低 |
| 8 | **工具并发执行** — 只读 skill 并发，写入 skill 串行 | 减少多工具调用延迟 | 中 |

### P2：成本与性能优化

| # | 优化项 | 预期收益 | 复杂度 |
|---|--------|---------|--------|
| 9 | **Prompt Cache** — 系统提示标记 cache_control，复用缓存 | 减少90%重复token成本 | 中 |
| 10 | **流式工具预执行** — 模型输出时就开始解析和执行工具 | 减少每轮等待时间 | 高 |
| 11 | **动态工具描述** — 工具描述从 prompt 移到 tools 参数 | 减少 prompt token | 低 |
| 12 | **task_budget** — 告知模型剩余 token 预算 | 避免输出超限 | 低 |

### P3：高级特性

| # | 优化项 | 预期收益 | 复杂度 |
|---|--------|---------|--------|
| 13 | **隐藏上下文注入** — 类似 `<system-reminder>` 机制，注入数据库元信息 | 更丰富的诊断依据 | 中 |
| 14 | **消息规范化** — 工具结果上浮、连续角色合并、格式验证 | 减少 API 错误 | 中 |
| 15 | **可观测性** — token用量/轮次/延迟/错误率遥测 | 优化依据 | 中 |
| 16 | **Auto Compact** — 长诊断自动压缩历史 | 支持更长诊断链 | 高 |

## 五、OpenDB 独有优势（应保留并强化）

1. **规则引擎兜底** — Claude Code 无此能力，OpenDB 在 LLM 失败时可降级到规则诊断，这是金融场景的关键可靠性保障
2. **能力分层适配** — small/large 能力分级 + GuidedStrategy/AutonomousStrategy 双策略，比 Claude Code 的"一刀切"更灵活
3. **收敛引导** — maxTurns-2 时注入收敛提示，比 Claude Code 纯靠模型自主判断更可控
4. **双路径工具调用** — AgentLoop(native) + PromptLoop(text模拟) 兼容弱模型，Claude Code 只支持 native
5. **数据压缩** — CompressReport() 将 150 帧爆发数据压缩到 ~2000 token 结构化摘要，这是领域特有能力
6. **安全分级** — L0-L3 四级安全 + readOnlyFilter，针对 DBA 场景设计
7. **模型无关架构** — 换模型只改配置不改代码，分层渐进放开

## 六、核心洞察

### Claude Code 为什么聪明？

不是因为 Opus 比其他模型聪明（虽然确实强），而是因为框架做了大量工作让模型"看到正确的东西"：

1. **信息充足** — 30+ 种自动附件，模型总是有足够的决策依据
2. **行为明确** — 30KB 系统提示，精确到"用 Read 而不是 cat"的粒度
3. **容错健壮** — 5层压缩 + 10次重试 + 模型降级，几乎不可能失败
4. **成本可控** — prompt cache 减90%成本，让大量上下文注入变得经济可行

### OpenDB 的优化本质是什么？

不是让 LLM 变聪明，而是 **给 LLM 提供足够多的、正确的信息，并教它如何使用这些信息**。

具体来说：
- **系统提示** = 教模型"怎么做"（行为规范、工具策略、输出格式）
- **上下文注入** = 告诉模型"现在面对什么"（数据库状态、历史数据、异常报告）
- **错误处理** = 保证"通信不断"（重试、降级、压缩）
- **工具执行** = 让模型"做得到"（并发、截断、预算）
