# 10-附 — 系统提示词优化详解：从 1200 字到 4750 字，每一项的来源

## 一、当前 OpenDB 两套提示词的问题

### 两套不统一

```
路径 1: AgentLoop（native function calling）
  → prompts.go: SystemPromptForDiagnose()
  → ~1200 字: 12 条规则 + 工具名列表 + 模式说明

路径 2: PromptLoop（文本模拟 ```action 块）
  → prompt_loop.go: promptLoopSystemPrompt
  → ~1800 字: 11 条规则 + 工具详细描述 + action 格式 + 参数用法

问题:
  1. 规则不一致 — 12条 vs 11条，少了"表格要简洁""不要多余空行"
  2. 工具描述不一致 — prompts.go 只有名字，prompt_loop.go 有详细描述
  3. 都缺少 — 推理策略、工具入口映射、深度路径、等待事件解读、环境信息
```

## 二、新版提示词结构

```
新版（一套，分层组合，~4750 字）:

  ┌─ 通用基座 (~3000字) ─────────────────────────┐
  │  身份定义                                      │
  │  核心原则 (4条)                                │
  │  推理策略 (6步流程 + 5个错误避免)               │
  │  工具使用策略 (入口映射 + 深度路径 + 组合原则)   │
  │  输出规范 (中间轮次 + 最终诊断 + 格式要求)      │
  │  安全约束                                      │
  └──────────────────────────────────────────────┘
  ┌─ Oracle 特定 (~1500字) ──────────────────────┐
  │  对象引用规则 (7条)                            │
  │  等待事件速查表 (16个)                          │
  │  关键视图参考 (10个)                            │
  │  参数修改注意 (5条)                             │
  │  常见 ORA 错误 (6个)                           │
  └──────────────────────────────────────────────┘
  ┌─ 模式修饰 (~150字) ─────────────────────────┐
  │  playbook / assist / auto                    │
  └──────────────────────────────────────────────┘
  ┌─ 环境信息 (~100字, 隐藏消息) ────────────────┐
  │  DB类型/版本/实例/时间/模式                    │
  └──────────────────────────────────────────────┘
```

## 三、逐段对比：现有 → 新版

### 身份定义

```
现有:
  "你是 OpenDB 数据库诊断专家。你的任务是分析 Oracle 数据库性能异常并给出诊断建议。"
  → 1 句话，笼统

新版:
  "你是 OpenDB 数据库诊断专家。你通过调用 OpenDB 提供的工具来采集数据库信息，
   基于证据进行链式推理，给出精准的诊断结论和可执行的修复方案。
   用户是专业 DBA，无需解释基础概念。"
  → 3 个关键信息：工具驱动、链式推理、用户是专业人士
  → "用户是专业 DBA" 让模型不会解释什么是等待事件
```

### 核心规则 → 拆分为 4 个层次

```
现有 12 条规则（混杂在一起）:
  1. 中文回复           ← 格式
  2. 先分析再结论       ← 推理
  3. 建议可操作         ← 输出
  4. 区分紧急和根因      ← 输出
  5. 结论要明确         ← 核心原则
  6. 给原生 SQL         ← 输出
  7. 不要列查询让用户跑  ← 推理错误
  8. 不要多余空行       ← 格式
  9. 表格要简洁         ← 格式
  10. 引用对象先验证     ← DB 特定
  11. ISEQ$$_ 处理      ← DB 特定
  12. 禁止编造数据       ← 核心原则
  → "中文回复"和"禁止编造"放同一级别，但重要性天差地别

新版拆分:
  核心原则 (4条) — 不可违反: 证据说话、禁止编造、先观察后判断、主动收敛
  推理策略 (6步+5避免) — 怎么思考
  工具策略 (入口+路径+原则) — 用什么工具
  输出格式 (中间轮+最终+格式) — 怎么输出
  安全约束 — 工具安全级别
  DB 特定 — Oracle/MySQL/PG 各自独立
  → 分层后模型能更好理解优先级
```

### 推理策略（全新）

```
现有: 无。模型自己摸索。

实际问题:
  ❌ 一上来调 health（太泛，浪费轮次）
  ❌ 查了 3 个工具不分析，继续查第 4 个
  ❌ 第 3 轮还在查 activesessions（前面已查过）
  ❌ 最后给出 "建议检查等待事件"（不是结论）

新版 6 步流程:
  1. 观察现象 → 2. 建立假设(2-3个)
  → 3. 收集证据(每轮1-2工具) → 4. 排除或确认
  → 5. 深入验证 → 6. 给出结论

新版 5 个错误避免:
  "不要看到一个异常指标就下结论"
  "不要一次查太多工具"
  "不要重复查同一个工具"
  "不要没数据就给建议"
  "不要列一堆查询让用户去执行"
```

### 工具入口选择（全新）

```
现有: 27 个工具名列表，无使用指引

新版: 7 种异常类型 → 首选工具
  性能下降 → activesessions + waits
  SQL 慢查 → topsql 或 slowsql
  锁等待   → locks 或 blocktree
  空间告警 → space
  CPU/IO 高 → os + waits
  数据库挂起 → activesessions
  错误/告警 → alert
```

### 深度分析路径（全新）

```
现有: 无。查完第一步后模型经常跑偏。

新版: 12 条 "发现 X → 下一步 Y":
  等待事件高  → ash → 找 SQL → explain
  全表扫描    → explain → tableinfo → 建索引
  行锁争用    → blocktree → 找阻塞源
  I/O 高      → os → topsql → explain
  内存不足    → sga + pga → params
  空间使用率高 → segments
  执行计划变化 → planhistory
  临时空间不足 → tempsess + sortusage
  Undo 不足   → undosess
  历史对比    → awr
  连接数异常  → sessions → resource
  ...
```

### 等待事件速查表（全新）

```
现有: 无。模型靠训练知识，小模型可能不知道。

新版: 16 个常见等待事件
  I/O: db file sequential read, db file scattered read, direct path read,
       direct path write temp, log file sync, log file parallel write
  锁:  enq: TX - row lock, enq: TM - contention, enq: TX - index contention
  内存: cursor: pin S wait on X, latch free, free buffer waits
  网络: SQL*Net message from client, SQL*Net more data from client
  每个含: 含义 + 典型根因 + 快速检查方向
```

### ORA 错误速查（全新）

```
现有: 无。

新版: 6 个高频错误 → 快速检查路径
  ORA-01555 → undosess + params undo_retention
  ORA-04031 → sga + params shared_pool_size
  ORA-01652 → tempsess + space
  ORA-01653 → space + segments
  ORA-00060 → alert + locks
  ORA-04030 → pga + params pga_aggregate_target
```

## 四、每一项优化的来源：Claude Code 借鉴 vs 自研

### 来源分类

| 优化项 | 来源 | 说明 |
|--------|------|------|
| **身份定义增强** | Claude Code 借鉴 | CC: "You are Claude Code, Anthropic's official CLI..." 精确定义角色+能力+用户 |
| **核心原则分层** | Claude Code 借鉴 | CC 的系统提示分层：身份→规则→任务指导→工具→语气→效率，不是扁平列表 |
| **推理策略(6步)** | 自研（DBA 领域） | CC 不需要教 Opus 怎么推理代码问题，但小模型需要教怎么推理数据库问题 |
| **推理错误避免(5条)** | Claude Code 借鉴 + 自研 | CC: "先诊断再换策略，不要盲目重试" + OpenDB 实测中观察到的具体错误 |
| **工具入口映射(7种)** | Claude Code 借鉴思路 | CC: "用Read不用cat，用Edit不用sed" — 精确到"什么场景用什么工具" |
| **深度分析路径(12条)** | 自研（DBA 领域） | CC 没有这个（代码诊断路径不固定），但 DB 诊断有固定套路 |
| **工具组合原则(4条)** | Claude Code 借鉴 | CC: "可以并行调独立工具""用Agent处理复杂任务" — 工具编排指引 |
| **中间轮次输出格式** | Claude Code 借鉴 | CC: 系统提示要求"高级别状态更新""只在关键节点更新" |
| **最终诊断3段格式** | 保留现有 | OpenDB 已有且验证有效 |
| **格式要求(紧凑/表格)** | 保留现有 | OpenDB 已有且验证有效 |
| **安全约束分级** | 保留现有 + 增强 | 现有分级好，增加按工具的具体说明 |
| **等待事件速查(16个)** | 自研（DBA 领域） | CC 不需要，这是纯 Oracle DBA 知识 |
| **ORA 错误速查(6个)** | 自研（DBA 领域） | CC 不需要，这是纯 Oracle DBA 知识 |
| **对象验证规则强化** | 保留现有 + 增强 | 现有规则好，增加 CDB/PDB 和更多场景 |
| **环境信息注入** | Claude Code 借鉴 | CC: prependUserContext() 注入 git status + 日期 |
| **IsMeta 隐藏消息** | Claude Code 借鉴 | CC: isMeta=true 模型看到用户看不到 |
| **用户自定义规则** | Claude Code 借鉴 | CC: CLAUDE.md 四级加载 → OpenDB: rules/ 三级加载 |
| **缓存分块** | Claude Code 借鉴 | CC: 系统提示分块，静态部分可缓存 |

### 来源统计

```
Claude Code 借鉴:     10 项（架构思路和通用模式）
自研（DBA 领域知识）:  4 项（推理策略/分析路径/等待事件/ORA错误）
保留现有 + 增强:       4 项（输出格式/格式要求/安全/对象验证）
总计:                  18 项
```

## 六、对诊断准确率的预估影响

```
小模型 (Qwen 9B):
  当前: 没有推理策略 → 经常跑偏、重复查询、给不出结论
  新版: 6步推理 + 入口映射 + 路径指引 → 像有经验的 DBA 带着走
  预估: 诊断完成率 ~40% → ~70%

中等模型 (27B Distilled):
  当前: 有一定推理能力但缺乏 DBA 领域知识
  新版: 等待事件速查 + ORA 错误参考 → 补上领域知识短板
  预估: 诊断准确率 ~60% → ~85%

大模型 (Opus/GPT-5):
  当前: 推理能力强但不知道 OpenDB 有哪些工具、怎么组合
  新版: 工具策略 + 深度路径 → 充分利用 OpenDB 的 40+ skill
  预估: 诊断效率（轮次数）~8轮 → ~5轮（更快收敛）
```
